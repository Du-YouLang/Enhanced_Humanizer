# ADR-0031 GRANGER 验收环境修复与源码复核

日期：2026-10-13。用户授权：解决 GRANGER 任务验收阶段的问题。GitHub 操作继续暂缓。

GRANGER 在模型生成、评分和选择全部冻结后，因控制器找不到 `threadpoolctl` 中断。该依赖已经存在于冻结的 GRANGER Python 3.11 环境，控制器则运行于 Python 3.12，并借用冻结 TMS 环境的 NumPy。修复仅加载现有纯 Python 限流模块，不把 Python 3.11 的整个 site-packages 加入控制器；依赖预检提前到模型生成和 GPU 验收之前。目录别名指向同一依赖文件时按真实路径去重，真实多份依赖或越界路径仍拒绝。

原检查器把所有 `.get()` 与 `cp.asnumpy()` 调用都当成回 CPU 回归。独立读取八份完整源码确认：DS0/E 的 `.get()` 是函数字典缓存，A/B 的 `.get()` 是字典缓存，A/B 的 `cp.asnumpy()` 只用于可选的边/窗口元数据转换。冻结协议给出主机元数据，该转换分支不会执行；信号、设计矩阵、求解及残差没有回 CPU 计算。一般字典例外采用保守绑定检查；元数据转换例外必须经过私有源码复核，绑定精确源码 SHA 和 AST 行号。实际 worker 中的回传拦截保持原样，不能通过复核免除数值或运行检查。

补充验收使用独立目录和入口，不覆盖原生主集的 59 份源码、环境、候选、评分、选择、失败和账本。第一轮恢复复用 C 已完成的 GPU 输出，完成 DS0/C/M/D/E/F 的数值检查；第二轮复用这六份数值结果，经实质 GPU 算法复核，仅补做 A/B 原先未执行的数值检查。原始拒绝与中间 INDETERMINATE 均保留，最终判定另存 `control/granger-reviewed-acceptance.json`。

八份候选以及冻结选择对应的 A–F 六臂全部通过。性能仍按同机 CPU 单线程、GPU 常驻及含传输边界分别记录，不把数值通过当作加速证明。原始模型墙钟区间缺失，继续标记 unavailable，不能用于端到端时延比较。候选间共享生成池，六臂通过也不是六个独立随机样本。

每个新结果都有持久化写入意图和精确哈希。再次执行最终验收入口只读取已完成回执，不重跑数值任务、不写日志、不调用模型。累计账本逐字一致：5557 次 DeepSeek 请求、178 个订阅实验回合、API 保守上界 USD99.7752408，实付 unavailable。修复新增模型调用为零，不退还历史未知预留。

本次完成 GRANGER 单题验收。完整 P6、Pi 对照、新版 P7 包及对外发布仍需各自验收。GitHub CI 尚未运行；当前结果是本机真实验收和本地代码验证。监控将历史批次中的 INFRA_FAIL 与补充回执的最终状态同时显示，历史索引不改写。详见 [GRANGER 验收审计](../audits/GRANGER-acceptance-2026-10-13.md)。
