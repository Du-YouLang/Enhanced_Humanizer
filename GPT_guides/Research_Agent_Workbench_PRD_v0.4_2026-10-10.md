# Research Agent Workbench — 累积产品需求总账 PRD v0.4

**日期**：2026-10-10  
**文档性质**：对当前讨论中多轮用户需求的累积整理；用于取代 PRD v0.3 作为*需求总账*，并非已经验证的技术架构或已经开发的软件。  
**关联实施文档**：`Codex_Research_Agent_Workbench_Implementation_Guide_v0.3.md`（仍可作为 P0 草案，但 Codex 须先按本 v0.4 核查差异，更新实施指导书至 v0.4 再进入后续阶段）。  
**权威规则**：用户最新明确决定 > 先前明确决定 > 本文中标记的技术建议；需求不能因为首版暂不实现而消失。任何更改须写入 ADR，并保留旧版本。

## 0. 需求来源、标签与设计边界

### 0.1 来源编号（用于追踪，不等于消息数量）

- **S1：最初动机**。低 Token 预算下，借鉴 NVIDIA GPU 算子优化工作与 Humanize，多强模型串行协同；研究 LLM-as-a-Verifier、TurboAgent 和同类项目；希望 DeepSeek 的高速度和低成本与 Sol/Astra 的高能力相结合。
- **S2：产品与技术定位**。Humanfia Humanize 作为总框架；DS-Enhanced 与 Sol/Astra 均可直接开发；DeepSeek V4.1 Flash 完成 N 次候选（N=3/4/5 可调），Sol/Astra 做验证；以后可按步骤切换模型，但首版只做 DS + Sol；讨论 Codex/CC Skills、DSH 现成 Harness 或自建 Harness；Web UI；小算力基准；参考 diagram-design 保存项目探索历程。
- **S3：16 项逐条修订**。运行效率及与原生 Harness 对照；高 Star/Fork 多智能体交接调研；可移动硬盘及项目记忆；人/Agent 职责；任务级多候选；Verifier + Reviewer + Merge；全失败处理；Jev；logprobs 限制；Git 版本和回滚；BugsInPy/SWE-Lite/科学任务；Benchmark 方案；上游 Fork/Star 致谢；GitHub 云端；独立上下文/上下文工程；探索图 UI。
- **S4：最近四项冻结决定**。Jev 作为候选评分接口，纳入对照；首轮本地 SSD，机械硬盘延期；首轮仅固定环境轨道；候选综合交给高能力 Reviewer 自主解决，而非预设机械合并规则。
- **S0：早期技术讨论中已明确的参考选择**。Humanize 的 RLAR/Flame Chase；Aider Architect/Editor、Agentless 局部补丁与 OpenEvolve/KDA 性能优化；原版 LLM-as-a-Verifier/TurboAgent 的作用边界；N 候选后选择或融合的成本—质量权衡。这些多数是设计参考或实验方向，并非全部已承诺为首版功能。

### 0.2 每项需求的标记

- **[C] 用户已经确认的产品要求**：原则上不得擅自删除、降低；首版或指定阶段必须实现。
- **[E] 必须通过实验回答的问题**：不能宣称已经有效；需明确对照与评价指标。
- **[P] 设计建议**：可依据实测/ADR 替换；不能伪称用户已做最终选择。
- **[F] 未来需求**：记录接口/路线，但首版不要求实现。
- **[O] 操作前待用户决定**：尚未提供必要信息，不能推测或自行代决策。

### 0.3 清晰的非目标

- 首版不重写整个 Coding Harness，不做通用多模型 SaaS，不强制同时运行多套大型 agent orchestration 框架。[C/P]
- 不假定 Best-of-N、Jev、强模型融合、串行轮换必定优于单模型；结果必须由真实任务/成本对照得出。[C/E]
- 不将医学研究代码直接视为临床可用工具；不使用测试集反馈持续调参。[C]
- 首版不建设可移动 WSL2 全套环境，也不要求先接实验室服务器。[C]

## 1. 产品使命与基本用户体验

**V-01 [C; S1/S2]** 面向个人高强度科研探索与复杂软件工程，目的是用有限的 DeepSeek 和 GPT Sol/Astra 配额，提高完成真实工程任务的成功率、交付速度和可追溯性，而非只提高聊天回答质量。

**V-02 [C; S1/S2]** DeepSeek 保留其快速响应/低成本的价值，Sol/Astra 不是“只给分的监督员”，而是能够直接阅读、重构、设计、实施、运行和优化工程代码的共同开发者。

**V-03 [C; S2]** 用户主要通过一个工作台定义目标、验收标准、预算和探索方向；观察、暂停、介入、恢复、审批或从历史节点重新分叉。

**V-04 [E; S1–S4]** 核心成功标准不等于 Top-1 分数：比较真实任务完成率、每成功任务总开销、端到端交付时间、人工干预及科研正确性；并报告是否优于基模各自官方/成熟 Harness。

**V-05 [C; S2]** 本轮主生成模型组合固定为 DeepSeek V4.1 Flash 与 GPT-6.1 Sol；Astra 作为可选高能力参考/未来升级。长期希望按工作流步骤改模型，但**不在第一版开发通用多模型配置平台**。

## 2. 工作流编排与强弱模型轮流开发

**WF-01 [C; S1/S2]** 优先复用 `humanfia/humanize` 作为*唯一*主编排框架。评估其现有 Flow 接口、暂停/恢复、预算、CLI/TUI/Web、日志和后端适配，优先增量扩展。

**WF-02 [C; S2/S3]** 至少两个真正可编辑的构建者：`DS-Enhanced` 和 `Sol-Builder`；能多轮串行接管同一项目并独立提出新方案，Sol 不能退化为只改局部 bug 的审查者。

**WF-03 [C; S3]** Sol-Builder、Sol-Verifier 与 Sol-Reviewer/Merger 为独立身份、独立上下文、独立预算；DeepSeek 各候选也独立会话。多个角色可使用同一底层模型，但不能暗中共享推理会话。

**WF-04 [P/E; S0]** 参考 Humanize 原生 `RLAR`（实现↔审查↔修复）和 `Flame Chase`（双方直接优化并交替进行）两种已有流程；基线先复现实测，再决定是否在自定义 Flow 中显式保留两个可切换运行模式。**这项模式对照在 v0.3 中没有作为独立规划写明。**

**WF-05 [C; S2/S3]** 强模型接力时可以彻底推翻上一版结构、回到更早检查点、选择替代设计；不强行规定一方只能在另一方代码上做增量修复。每轮结果需要重新测试。

**WF-06 [P; S0/S3]** 任务交接以标准化工程工件为核心而不是共享完整对话；支持“下一个由谁做什么、为什么”和人工改变交接方向。借鉴 MetaGPT、AutoGen、CrewAI、Gas Town、Beads、LangGraph 等思想，但不一次引入多个编排器。

**WF-07 [C/P; S1/S3]** 设置任务通过即停、时间/Token/费用用尽停止、连续多轮无进步停止、人工暂停、基础设施失败等状态；从暂停/失败处可恢复。建议默认短轮次、按需要升级复杂流程。

**WF-08 [F; S2]** 后续允许每一步指定执行模型、增强模型、Reviewer/Judge 模型，并新增模型供应商；第一版仅预留配置字段与适配接口，不实现全部排列组合。

## 3. DS-Enhanced 与多候选探索

**DS-01 [C; S2/S3]** 对一个已定义的工程任务，DeepSeek 运行 N 个独立完整 Coding Agent 候选，N=3、4、5 由用户配置，N=1 作为关闭增强的对照；默认 N=3 仅是首版推荐值。

**DS-02 [C; S3]** 候选任务粒度可以是小型局部工程修改，也可以是从零开发整个小项目。候选不能仅仅是采样 N 段普通回答；各自必须有代码、工具执行、测试和可恢复版本。

**DS-03 [C; S3]** 在相同起始 Git commit/任务合同上运行，候选 A…N 采用独立 worktree、独立进程/Session、日志和预算；可并行；防止写入互相污染与读取其他候选结果。

**DS-04 [C; S3]** 固定、记录每个候选的模型 ID、Harness、提示词/配置哈希、Git SHA、测试、日志、Token/费用、启动—结束时间、失败类型及产物。

**DS-05 [E; S0/S1]** 官方原版 LLM-as-a-Verifier 的核心是细粒度概率评分与候选排序，它*没有被证明*能让 DS 每一轮的基础模型能力提升。应对相同候选池明确比较：自动测试、原版 LAV、Jev、Sol 结构化评判，以及新增 Merge 的额外收益。

**DS-06 [P/E; S0/S2]** TurboAgent 的“每次 API 回复 N 采样”作为*独立对照/未来可选增强粒度*保留，不应取代本轮确认的任务级 N 路执行。比较延迟、总 Token、真实成功率之后再决定是否值得支持。

**DS-07 [C; S3]** 各候选先按冻结测试器执行客观测试。失败候选仍然存档并送给 Reviewer；不能默认全部丢弃。对于全部失败，不能将“相对最好”当作完成。

**DS-08 [C; S3]** 若所有候选失败，系统输出结构化原因、失败复现、共同缺陷、每个候选的局部亮点与下一轮建议。允许 Reviewer 继续独立重新实现 M；若 M 也失败，保持 FAIL/INDETERMINATE，按预算重试或上报。

**DS-09 [E; S1/S3]** 必须测 DS-Enhanced 是否仍然保持原生 DeepSeek 在 CC/Codex/DSH 中的低延迟体验；监控并发限流、排队、测试时间、Reviewer/Judge 增加的延迟；不得只报告 DS 单请求生成速度。

**DS-10 [P; S0]** 原版 LAV `ProgressTracker` 可用于判断进度/是否应提前放弃候选，但不应仅凭未经校准的评分终止可能成功的任务。可列为后续特性试验。

## 4. Verifier、Jev 与 Reviewer 合成

**JR-01 [C; S2–S4]** 至少有三条评分比较路线：`J0` 自动测试/规则筛选，`J1` 原版 LAV 概率评分，`J2` Jev-as-a-Judge，`J3` Sol 独立结构化评分；统一冻结候选池与 Rubric 做 Judge ablation。

**JR-02 [C; S3/S4]** Jev 是待验证的候选接口，不预设替代原版，也不能把 Jev 的结构化判断称为原版概率期望分数。检查真实 API 可用性、正确率、胜负排序、幻觉/误判、成本、延迟与失败处理。

**JR-03 [C; S3]** 原版 LAV 依赖可返回评分 Token 的 logprobs 的后端；Sol/Astra 如接口不提供 logprobs，则不可原样代替评分模型。可以使用 Sol 直接结构化判断，或使用 Sol 分析 + 支持 logprobs 的后端评分的两阶段方案，**分别标记算法身份**。

**JR-04 [C; S3/S4]** Sol-Reviewer 必须阅读所有候选，包括失败代码、局部通过证据、错误和执行摘要；可以自主综合设计、选择部分实现、推翻所有实现或在新分支重新实现 M。不能人为限制为机械拼接。

**JR-05 [C; S3/S4]** 候选 M 是一个*新的完整实现*，单独 commit/worktree，经过与 A…N 相同的硬测试，公平比较，不保证 M 必然优于原候选。

**JR-06 [C; S3]** 若候选之间不可组合，Reviewer 应报告技术冲突、保持多个备选并提出替代路线，不强行创建不可工作的“集大成”版本。

**JR-07 [E; S3/S4]** 对冻结候选池开展 `Best-of-N` vs `Best-of-N + Sol-Reviewer-M` 消融；覆盖部分成功、全部失败、不兼容候选；计入 Reviewer/M 的额外 Token 与时间。

**JR-08 [P; S1/S3]** 评分和综合优先使用结构化、可追溯的代码差异、测试证据和风险摘要；复杂分歧可展开原始轨迹。避免每次重读五份极长对话导致 Token 预算爆炸。

**JR-09 [F/P; S0]** 以后可在高难度场景额外引入 Astra 作为仲裁/Reviewer；首版不强制占用 Astra 配额。

## 5. Harness、外部接口与运行环境

**HR-01 [C; S2]** 先检查“CC/Codex Skills 插件方案 vs 现成 DSH/Codex Harness 增量开发 vs 自建 Harness”的取舍；已选优先路线为 Humanize Flow + DSH 执行 DS + Codex Harness 执行 Sol。Skills 用作必要时的辅助，不承担跨角色编排主体。

**HR-02 [C; S2/S3]** 实际验证模型及 CLI/SDK 能否执行文件读写、命令、测试、提交、记录 token、限制费用、恢复会话；版本锁定，保存真实能力矩阵。未验证的 API 兼容性不算已完成。

**HR-03 [C; S4]** 首轮所有源代码、worktrees、WSL2 虚拟磁盘（如需）、Conda/uv、SQLite、日志及项目独立 memory 存放本地内置 SSD；外置机械硬盘不参与第一轮。

**HR-04 [F; S3]** 后续可将环境/数据/记忆移到外置 HDD 或实验室服务器；但 WSL2 注册、路径迁移、HDD I/O、热插拔风险和备份机制须另立项，不视为当前已支持“即插即用”。

**HR-05 [C; S3/S4]** 第一轮 Benchmark 使用预先设置并冻结的环境。Codex 配置依赖，必要的账户/系统权限先问用户；历史仓库需要按实例隔离环境时允许多个**预先固定的** conda env/容器，不强迫一个环境强行兼容所有旧版本。

**HR-06 [F; S3/S4]** 若首轮 benchmark 过易、不足以辨别能力，再计划新 benchmark 和允许 agent 自己配置环境的第二轨；第一轮不把环境自治计入模型能力。

**HR-07 [C/P; S3]** 用户自己的 Token、订阅额度和 API 费用是主要现实约束。每个角色、候选和任务应记录输入/输出/缓存/token 可见性、API 费用或订阅使用（两者不直接混算现金），并具备预算熔断。

## 6. 高质量上下文与项目记忆（独立于官方聊天记忆）

**CX-01 [C; S2/S3]** 项目的工程记忆、对话证据、决策、任务与 Git 关联独立于 Codex/CC 原生 Memory，位于本地项目可迁移目录，可导出/备份/恢复。

**CX-02 [C; S3]** Builder / Reviewer / Verifier 各有独立角色约束及会话。交接不是完整聊天拼接，而是可追踪的结构化包（当前 commit、已验证事实、猜测、被证伪路线、测试、未解决问题、下一步、预算）。

**CX-03 [C/P; S3]** 建议 SQLite 索引任务/决策/依赖 + append-only NDJSON 保存事件 + 实际产物目录保存完整工具轨迹、Diff、测试、审查、模型配置和人工指令；摘要不能覆盖原始证据。

**CX-04 [C; S3]** 研究历史至少包含：问题、根因假说、证据、实施尝试、为何失败、为何放弃、何时重启、解决方案和后继任务；区分 `fact / hypothesis / rejected / superseded / unresolved`，每条支持返回来源证据。

**CX-05 [P; S0/S3]** 借鉴 MetaGPT 标准工件、Beads 依赖图、Gas Town 持久任务交接、LangGraph checkpoint、上下文工程资料；仅提取机制，不必把它们都加入运行依赖。

**CX-06 [P/E; S3]** 上下文质量必须可评测：测平均上下文 Token、重复读取比例、正确获取历史失败的召回率、因历史摘要错误导致的返工率；可作为后续诊断，不必进入首轮四项主指标。

## 7. GitHub、代码版本、审计、回滚与开源致谢

**GC-01 [C; S3]** 项目从 P0 就通过用户授权的 GitHub 账号建立自己的远程仓库并维护 Issue/Branch/PR/CI、分支保护、定期 Push 和回滚能力。账户可见性、仓库名称、授权范围须用户确认。

**GC-02 [C; S3]** 一个 Issue 表达工程目标；一个正式 PR 汇总可验收成果；一个任务可同时有多个候选分支、融合分支和 Sol 接力分支；不要每个模型回复都建 PR。

**GC-03 [C; S3]** 候选 A…N、M、Sol-Builder 工作分别采用独立 worktree/branch；保存 base SHA、head SHA、审查/测试和 PR 关联；主分支只经 CI 与人工审批合并。

**GC-04 [C; S3]** 保留所有有意义的代码历史，包括失败候选的可恢复 Git refs 与完整运行元数据；支持 revert、从任意已保存节点分叉、回滚演练；避免自动清理导致历史丢失。

**GC-05 [C; S3]** Codex 使用用户本人授权的 GitHub 账号 Fork 实际参与源码开发/复现的上游项目，并保留 upstream URL、commit、许可证、用途；未经用户授权不得代其批量 Fork 或 Star。最后给用户重点参考项目清单供其自行 Star。

**GC-06 [C; S3]** `.gitignore`、机密扫描和隐私审计为强制项；不能把 API 密钥、虚拟磁盘、Conda 缓存、大型原始科研数据或敏感材料直接推送 GitHub。

**GC-07 [C/P; S3]** 对破坏性 Git/文件操作使用外部安全门禁，检测工作树未提交改动，先保存 checkpoint 或请求用户授权；仅写 Prompt“不准删除”不足以保护文件。

## 8. UI：可视化探索图与 Human-in-the-loop

**UI-01 [C; S2/S3]** 工程探索图是核心交互界面；能看到任务及子任务、多个候选、各自测试、Reviewer 判断、融合版本、接力开发、失败、预算与时间，以及人工决策。

**UI-02 [C; S2/S3]** 点击节点需能展开 Git Diff/commit、完整或摘要执行日志、测试、结论证据、Issue/PR、父子和依赖关系；用户能够添加注释、拒绝、批准、暂停/恢复和从此节点启动新的分叉。

**UI-03 [C; S3]** `cathrynlavery/diagram-design` 提供美学参考与图表导出约束，不应误认为支持自动日志存储或实时交互。首版优先扩展 Humanize Web，画布可用 React Flow 等组件，实际数据来自结构化事件仓库。

**UI-04 [C; S3]** UI 可多轮迭代，第一版先可用再优化；不必在首轮开发独立 Electron 客户端或自动生成精美静态海报。

**UI-05 [P; S2/S3]** 顶栏状态与预算、左栏项目/任务树、中央可缩放探索画布、右栏节点证据/代码差异、底栏用户命令；可以依据真实测试修改布局。

**UI-06 [C/P; S3]** 界面不只是历史回放，也是执行控制台：启动/停止、设置 N 和预算、选择历史节点恢复、人工改变下一轮路线。审批必须由后端硬性执行，不以 UI 按钮作为唯一安全保障。

## 9. Benchmark：受控、轻量、真实智能需求

**BM-01 [C; S2–S4]** 首轮固定 16 项：BugsInPy×6、SWE-bench Lite×6、科学编程×4；不要求用户提前积累十几个高难个人科研历史项目。

**BM-02 [C; S3]** 科学四项：①PC_ALM 轻量复现；②基于用户指定论文实现卒中诊断/分析代码、输出数值表格和图像；③Exponential Gradient Learning 轻量复现、重建原论文表格和图像；④CPU Granger Causality 改为 CuPy GPU 实现，验证数值精度和性能。

**BM-03 [C; S4]** 首轮由 Codex 统一准备固定环境；每个任务/基准实例跨模型、跨配置使用同样环境。依赖版本冲突时可以为不同任务预建独立环境。若要用户介入环境设置，先说明。

**BM-04 [C; S3]** A=DS 原生 DSH、B=DS×N+自动测试、C=DS-Enhanced、D=Sol 原生 Codex、E=DS+Sol Humanize、F=DS-Enhanced+Sol Humanize；另保留 DS 原生 CC/Codex Harness 的速度参照（如可用）。

**BM-05 [C; S4]** Judge 消融：同一批候选，自动测试/规则 vs LAV 原版 vs Jev vs Sol；比较排序/正确性、误判、费用、延迟。Merge 消融：Best-of-N vs Best-of-N+Sol-Reviewer-M。

**BM-06 [C; S2/S3]** 主指标：完成率、每成功任务总成本、端到端时间、人工干预。次指标：TTFT、首个可运行补丁、首个测试通过、最终交付、候选生成/测试/Judge/Reviewer/Sol-Builder/CI 延时拆分、吞吐、Token、p50/p90。

**BM-07 [C; S3]** 衡量实际系统效率，不能仅测模型 token/s。公平比较固定任务/初始代码/工具权限/硬件/实际预算，提供等成本与等时长分析，报告逐任务结果和失败类别，不夸大 16 项小样本的统计显著性。

**BM-08 [C; S3]** 科学实验不能只用图像相似度或是否输出文件验收；必须参考可执行金标准、数值容差、统计不变量、协议准确性；GPU 任务记录硬件/驱动/CuPy/CUDA 和浮点误差。

**BM-09 [C; S3]** 任务环境失败 `INFRA_FAIL`、能力失败 `FAIL`、超时 `TIMEOUT`、无法判断 `INDETERMINATE` 区分报告；不要把缺论文、缺 GPU 或 API 凭据伪报为模型失败。

**BM-10 [O; S3/S4]** 四项科研任务的确切论文/输入数据/代码基线/数值表格尚需用户在评测前给出；不得虚构材料，可先跑 12 项公共任务或先做 smoke test。

**BM-11 [E; S0]** 可另设轻量低成本的局部补丁 vs 全任务重试比较（借鉴 Agentless），及强模型设计→廉价模型执行 vs 轮换（借鉴 Aider）。是后续对照建议，**不属于用户确认的首轮必跑实验**。

**BM-12 [F; S4]** 如果固定环境 16 项不够区分系统，再新增有挑战性的任务/环境自主管理轨道；首轮不强迫完成第二轨。

## 10. 成本/速度控制及分层探索策略

**OP-01 [C; S1/S3]** 对 N 候选并发、任务轮次数、Reviewer 生成 M、Jev/LAV 多次评分、Sol 接力分别设置可见预算与耗时上限，支持用户覆盖。预算用尽应优雅停止、保存工作产物。

**OP-02 [P; S0]** 建议提供低成本/常规/深度三种运行预设：①单 DS + 自动测试，②DS N + Judge/Reviewer，③DS-Enhanced↔Sol 长期轮换。**不自动默认开启最贵组合**，实际门槛通过 Benchmark 校准。

**OP-03 [C/E; S1]** 对比同任务下 DeepSeek 在 CC/Codex/DSH/Humanize 中的速度与响应流畅度；根据真实墙钟判断增强后的吞吐是否仍值得。

**OP-04 [P; S0/S3]** 可先用低成本规则/测试做第一轮筛选，减少 Sol 需要阅读的候选内容；保留失败候选供诊断。若涉及科研方法有效性争议，不能用廉价 Judge 的分数取代独立审计。

**OP-05 [F; S0]** 面向 GPU 算子、数值性能任务，未来可采用 OpenEvolve/NVIDIA KDA 的测试驱动搜索与持续优化循环，但不将其等同于通用科研假设选择。

## 11. 安全、伦理、人工审批和科研证据

**SG-01 [C; S3]** Humanize 可启动高权限编程 Agent；必须使用权限受限的隔离工作区/进程或容器、最小权限凭据、拒绝直接修改主分支，明确无完全隔离时的真实风险，不得用提示词冒充安全边界。

**SG-02 [C; S3]** 用户负责最终科研正确性、产品目标、账号/费用和敏感资料授权。Codex 负责实施、测试、仓库运维、PR/Issue、审计、上游清单和运行报告；仅在必须人工授权/重大方向争议时打断用户。

**SG-03 [C; S3]** 主分支合并、公开仓库、额外购买 API、安装/清理高风险操作、敏感科研数据上传必须有人工批准。不可让 Agent 在未经授权下无限循环和花费。

**SG-04 [C; S1/S3]** 研究任务必须保留完整正负结果，防止测试集泄漏/选择性报告/错误归因。审查记录要区分客观测试和语言模型意见。

**SG-05 [P; S1/S3]** 对神经科学特有协议（例如分组数据划分、标准化只用训练集、删失/风险集、随机种子报告）提供可编写的科研不变量模板；由具体任务决定是否启用，不应默认把某个实验的约束强加给所有项目。

## 12. 首版交付阶段与关键验收

- **P0 环境/仓库/接口**：确认用户 GitHub 身份/可见性，仓库与 CI，安全、上游版本锁、DSH/Codex/Humanize/Jev/LAV 真接口能力、成本预算；不得私下上传研究数据。
- **P1 Humanize 双 Builder**：DeepSeek 与 Sol 各自真正修改/测试并独立交接；验证官方 Harness 与 Humanize 的性能开销；RLAR/Flame Chase 可作为复用对照而非直接重新发明。
- **P2 DS-Enhanced 多路候选/评分**：N=1/3/4/5，独立 worktree、客观测试、J0-J3 接口、正常失败路径，记录延迟与成本。Jev/LAV 不可用时明确阻塞，但其余系统可工作。
- **P3 Sol-Reviewer 生成 M + 双方接力**：包括成功/失败候选，允许强模型自主重新设计；M 与各候选独立复测，全失败能交付故障分析而非虚假成功；Sol-Builder 可继续重构。
- **P4 工程记忆与 Git**：SQLite/NDJSON、关键事件/日志/解释证据、各角色 handoff，Git/Issue/PR 对应，合法历史回退与从节点分叉。
- **P5 首版 Web UI**：可视化探索图+状态/预算/延迟，节点关联代码/测试/审查，人工暂停、批准、拒绝、从节点继续。
- **P6 Benchmark**：冻结 16 项，完成 A-F 及 Judge/Merge 消融，包含 DS 原生 Harness 时延基线；所有结果按任务与费用/墙钟报告，诚实讨论失败与限制。

### 12.1 最小端到端验收场景（跨阶段）

1. 同一任务 DS N=3 的三个候选均产出真实代码与 Git commit，互不污染；任一失败候选仍能打开。
2. Sol-Reviewer 读取三候选优缺点，按自身判断生成新实现 M，实际运行相同测试。
3. 三候选都失败时，系统保留分支、生成诊断，并且不报告成功。
4. Sol-Builder 接管选中的候选或 M，再次真实编辑并测试，不只是打分。
5. 可恢复到任意合法 checkpoint，从该版本再次生成候选；主分支未被破坏。
6. 用户能在 UI 查看问题、方案、证据、费用、耗时，提交评论并暂停后恢复。
7. 同一批候选由 J0/J1/J2/J3 比较，缺失 Jev 凭据/不支持 logprobs 被明确标记而非伪造。
8. 在固定环境中可以对相同任务执行原生模型与完整系统对比，报告端到端速度与成本，不只报告单次生成延迟。
9. GitHub 仓库含相关 Issue/PR/CI 和上游出处，使用获授权的用户账号，敏感文件没有意外推送。
